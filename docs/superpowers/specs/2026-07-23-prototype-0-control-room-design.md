# 原型 0 控制室设计

## 目标

构建一个可在浏览器中完整演示的 Agent 控制室前端。它使用内存假数据模拟多 Agent 的任务、会话、审查和人工决定，但不运行真实 Runtime、不创建 worktree、不访问 Git 或本地进程。

用户在三分钟内应能理解并走完以下路径：观察多人席位与任务状态，选中一个任务查看上下文，为等待输入的任务作出决定，并接受或驳回一个待审查结果。

## 范围

包含：

- 单页控制室。
- 三个 Agent 席位：实现者、测试者、审查者。
- 四个任务，分别覆盖待开始、执行中、等待输入、审查中。
- 任务看板、任务时间轨、改动文件、测试输出、diff 摘要和活动记录。
- 请求总结、需要决策、发送反馈、接受和驳回五种可见状态变化。
- 响应式布局与键盘可达的操作控件。

不包含：

- 真实 Agent Runtime、命令执行、终端或 WebSocket。
- worktree、Git 命令、文件系统访问、SQLite 或网络请求。
- 创建任务、编辑席位、跨任务并行调度、用户账户或持久化。

## 架构

应用为 Vite、React 和 TypeScript 单页程序。领域对象、用例、端口、内存适配器和 UI 分层，依赖方向始终从 UI 指向应用层，再指向端口，最后由内存适配器实现端口。

```text
ui -> application -> ports <- adapters
               -> domain
```

- `domain`：只定义 `Task`、`AgentSeat`、`SessionEvent`、`ReviewDecision` 和状态联合类型，不依赖 React 或数据来源。
- `ports`：定义读取控制室快照、追加会话事件、更新任务状态和记录人工决定的接口。
- `application`：定义加载控制室、请求总结、标记等待输入、发送反馈、接受和驳回这六个用例；每个用例仅依赖端口。
- `adapters`：提供内存数据和内存仓储实现，作为原型 0 唯一可变数据源。
- `ui`：使用一个 React hook 调用用例并渲染；组件不导入假数据，也不直接修改领域对象。

原型 1 将保留 `domain`、`ports` 和 `application`，以本地 HTTP/WebSocket、SQLite 与 Runtime 适配器替换 `adapters`。UI 的任务卡、时间轨和审查抽屉不应知道这种替换。

## 数据与交互

初始快照包含：

- 实现者正在执行“重构身份验证中间件”。
- 测试者正在等待人决定是否覆盖旧版登录分支。
- 审查者的“审查速率限制改动”处于审查中，并有 diff 摘要和测试结果。
- 一个待开始任务用于表达队列与工作归属。

选择任意任务会更新右侧详情区域。所有交互按以下规则处理：

| 动作 | 前置状态 | 结果 |
| --- | --- | --- |
| 请求总结 | 执行中 | 在时间轨追加总结事件和一条活动记录 |
| 需要决策 | 执行中 | 任务变为等待输入，并追加检查点事件 |
| 发送反馈 | 等待输入或审查中 | 追加人工反馈事件，输入框清空 |
| 接受 | 审查中 | 任务变为已接受，写入人工决定和活动记录 |
| 驳回 | 审查中 | 任务变为已驳回，写入人工决定和活动记录 |

对不满足前置状态的动作，控件不可用，而不是静默失败。每个决定都要出现在右侧时间轨和底部活动记录中。

## 信息与视觉设计

控制室采用高密度工程操作台，而不是营销页面或大卡片看板。

```text
┌──────────────┬──────────────────────────────┬──────────────────────────┐
│ 项目与席位    │ 任务看板                       │ 所选任务的时间轨与审查区   │
│              │ 待开始 / 执行中 / 等待 / 审查中 │ 日志、产物、决定、操作      │
│ 活动摘要      │                                │                          │
└──────────────┴──────────────────────────────┴──────────────────────────┘
```

窄屏时左侧栏折叠为顶部项目条，中央看板保留横向滚动，详情区域位于看板下方。详情不可通过悬浮或颜色单独传达状态，所有状态都要有文字标签。

视觉令牌：

- 画布：雾灰 `#EEF1EF`。
- 表面：浅石灰 `#F9FAF8`，边界为 `#CCD4CF`。
- 主文字：墨绿黑 `#1C2925`，次级文字为 `#60706A`。
- 运行：青绿 `#007E71`。
- 等待输入：琥珀 `#A85A00`。
- 审查与人工决定：蓝绿 `#1C5E78`。
- 失败或驳回：洋红红 `#B42A50`。

字体使用系统无衬线字体，数字、日志和状态时间使用等宽字体。圆角最大 8px。唯一的高辨识度元素是任务时间轨：它按真实事件顺序把 Agent 输出、产物和人工决定串起来，让“人仍在控制中”成为视觉事实。

## 组件边界

- `ControlRoomPage`：装配数据、布局和选中任务状态。
- `ProjectSidebar`：项目名称、席位状态和近期活动摘要。
- `TaskBoard`：按状态列展示任务，并发出任务选择事件。
- `TaskCard`：显示负责人、状态、短摘要和最后更新时间。
- `TaskInspector`：显示所选任务的会话时间轨、产物和操作。
- `Timeline`：纯展示型事件序列。
- `ReviewActions`：只负责触发反馈、接受和驳回。

组件通过明确定义的 props 交互。状态变更动作集中在 `useControlRoom` hook 中，避免在卡片或时间轨组件里埋业务规则。

## 异常与空状态

- 未选择任务：详情区域展示“选择一个任务查看会话与审查记录”。
- 空反馈：发送按钮禁用。
- 已完成任务：所有会改变状态的操作禁用，但历史保持可见。
- 尚无活动：活动区域展示明确的空状态，不使用装饰性占位内容。

## 验收与测试

单元测试覆盖应用用例而非 React 实现细节：

- 请求总结在正确任务上追加事件与活动。
- 需要决策仅能把执行中任务转为等待输入。
- 接受和驳回只允许在审查中任务上执行，并保存决定。
- 发送反馈会写入事件且拒绝空内容。

组件测试覆盖用户可见行为：

- 初始画面同时显示三个席位、四个状态列和一个选中任务。
- 选择任务后详情区域更新。
- 点击接受后，任务卡和活动记录都反映“已接受”。
- 在错误状态下，操作按钮为禁用状态。

浏览器验收使用 gstack：在桌面与移动视口截图，走一次“选择审查任务、接受、检查活动记录”的路径，并检查控制台没有错误。

## 完成定义

满足以下全部条件才算原型 0 完成：

1. 可通过一个本地命令启动应用。
2. 不依赖网络、密钥或真实 Runtime。
3. 假数据只能由内存适配器提供，UI 不可直接导入。
4. 五种交互动作按照本设计更新可见状态与活动记录。
5. 单元测试和组件测试通过。
6. gstack 在桌面和移动视口下验证核心路径及无控制台错误。
