架构重构说明

这份文档从当前代码出发，说明为什么需要重构、要把边界放在哪里，以及如何用低风险的阶段性迁移完成它。目标不是把本地单体拆成分布式系统，而是让它在持续运行、任务增多、会话规则变复杂时仍然可控。

一句话结论

现有架构适合产品验证，但不适合继续堆叠执行与协作能力。 当前项目已经有 Domain / Application / Ports / Adapters 的分层意识；真正的问题是运行时控制、持久化访问、HTTP 聚合读取和前端刷新都集中在少数几个入口中，导致故障恢复和功能扩展的改动面过大。

保留

本地单进程部署、SQLite、Runtime Adapter、Git worktree、SSE。这些选择和产品定位一致。

调整

执行器需要持久化所有权；Repository 需要按上下文拆分；读取需要从全量快照改为范围化查询。

不做

本轮不引入微服务、消息队列、远程 worker 或通用事件溯源。复杂度要服务于本地可靠性。

当前结构与请求路径

服务端的目录结构已经清楚地区分了领域、应用、端口和适配器；问题在于关键路径仍会跨越这些边界，最终汇聚到少数大型类。

关键问题

P1 可靠性

Runtime 的所有权只存在于内存

TaskExecutionCoordinator 通过内存 Map 保存 session、timer 和 execution。服务异常退出后，数据库有租约，但没有可验证的进程所有权、PID 或恢复策略。

租约过期后任务会被重新排队；新执行会复用已有 worktree。若旧 Runtime 仍在运行，两个进程可能同时写同一目录。

P2 可维护性

一个 Repository 覆盖全部业务

WorkspaceRepositories 同时负责频道、成员关系、任务、租约、会话、记忆和 Dream。应用服务无法只依赖自己需要的能力，SQLite 实现也成为超大型文件。

P2 可维护性

会话编排器混合了六类职责

参与者选择、优先队列、Runtime 调用、持久化状态机、恢复、取消和事件发布都在 ChannelTurnCoordinator 中。任何新规则都容易触及整条会话生命周期。

P2 扩展性

所有事件都刷新完整 bootstrap

SSE 收到事件后，前端重新拉取整个 WorkspaceSnapshot。这个快照包含所有任务，任务历史越多，Runtime 输出越频繁，主线程和 SQLite 的压力越大。

P2 模型一致性

全局实体仍依赖旧归属字段

产品语义中 Agent 和 Channel 是全局实体，但创建时仍以最早的 Workspace 或 Repository 作为隐藏外键锚点。这会把历史模型残留带进所有后续规则。

P3 边界清晰度

端口层引用了适配器类型

Runtime 类型定义位于 adapter 下，ports 与 application 反向引用它。适配器替换和测试可以继续做，但依赖方向已经不再严格。

目标架构

目标仍是一个本地进程，但要把“业务状态”“外部副作用”“读模型”分开。数据库是状态的唯一来源；进程与 Git 操作由可审计的执行层管理；SSE 只通知数据发生变化，不承担同步全部状态的职责。

分阶段迁移计划

每阶段都保持可运行、可测试、可回滚。不要先进行目录级大搬迁；先建立新接口，让现有逻辑逐步迁移过去。

01

执行可靠性

引入 ExecutionRepository 和 ExecutionManager，持久化 execution、worktree reservation、PID、启动时间、心跳时间和终止原因。Task coordinator 改为只驱动 manager。

  • 同一 worktree 在同一时刻只能被一个 active execution 持有。
  • 启动、取消、超时和崩溃恢复必须都留下持久化事件。
  • 重启测试覆盖“旧进程仍在”和“旧进程已消失”两种情况。
02

拆分写模型与 Repository

先提取 TaskRepository、ExecutionRepository、ChannelRepository。SQLite 仍可共享同一个数据库对象和事务实现，但应用服务只接收自身最小依赖。

  • 保留一个基础 UnitOfWork，不保留一个全能业务接口。
  • SQLite 文件按上下文拆成 store、mapper 和 query 文件。
  • Runtime profile 类型移动到 ports 或 shared contract，消除 ports 对 adapter 的依赖。
03

会话编排解耦

将 ChannelTurnCoordinator 分为 planner、runner、recovery 和 state writer。保留现有持久化结构，先改变依赖关系，再考虑优化数据表。

  • Planner 输出下一批 invocation，而不直接执行 Runtime。
  • Runner 只执行一条 invocation 并写回结果。
  • Recovery 只处理未完成 turn 的认领和续租。
04

读模型与 API 收敛

将 bootstrap 缩小为侧栏与当前选择摘要；频道消息、任务详情、运行活动改为独立查询。SSE 事件携带实体类型与 id，前端只失效对应查询。

  • 任务列表必须分页或按频道与状态过滤。
  • 前端不再把全站数据放在一个 snapshot 中。
  • 按资源拆 controller，app.ts 仅保留 composition root。

重构约束与验收

必须保持的产品行为

  • 本地服务仍只监听 loopback 地址。
  • Runtime adapter 仍可替换，现有 Claude Code、Pi、OpenCode 配置不破坏。
  • 任务仍在独立 Git worktree 中执行，验收不自动 merge。
  • 现有 SQLite 数据可升级，不要求用户重建数据目录。
  • 现有 SSE 用户体验不下降，连接重建后能恢复当前可见状态。

每阶段的工程验收

  • 新增迁移具备版本号，启动时通过外键检查。
  • 每个新用例依赖小型 port，不接受全能 Repository。
  • 为崩溃、重启、租约超时和重复请求编写集成测试。
  • 运行 npm run test:run 与 npm run build。
  • 代码变更后更新本文件中的“当前状态”和迁移进度。
本轮最大的禁区 不要在没有持久化 execution ownership 的前提下，通过缩短租约或增加自动重试来“修复”卡住任务。那会提高旧 Runtime 与新 Runtime 并发写同一 worktree 的概率。

建议的首个实现切口

从阶段 01 开始：只为任务执行新增持久化 execution 和 worktree reservation，不先动会话系统与前端。它直接消除最高风险，同时建立后续拆分 Repository 所需的清晰事务边界。
