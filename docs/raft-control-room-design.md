# 设计文档：受 Raft 启发的 Agent 控制室

生成日期：2026-07-23  
分支：main  
仓库：Sinapsis  
状态：草案  
模式：个人项目探索

## 一句话定义

> 一个本地优先的控制室，让开发者能在同一个代码仓库中指挥、观察、打断、审查多个编码 Agent 的工作。

它不是新的 Agent Runtime，也不是泛化的“多 Agent 协作平台”。它把 Claude Code、Codex CLI、OpenCode 等现有本地命令行 Agent 当作可替换的执行者，把人放在任务分配、过程干预和最终验收的位置。

## 问题

目标用户是已经在使用多个编码 Agent 的开发者。今天他们通常要在多个终端、多个 worktree、多个聊天窗口之间切换，因此很难回答几个最基本的问题：

- 每个 Agent 此刻在做什么？
- 哪个任务已经被谁领取？
- 它改了哪些文件，是否卡住，是否需要我决定？
- 在改动进入仓库前，我该如何集中审查？
- 多个并行任务结束后，有哪些上下文和决定值得留下？

Raft 把人和 Agent 放在同一个协作工作区。它的启发不在于复刻频道或聊天，而在于把 Agent 视作有持续身份、任务、历史与工作位置的成员。本产品应把这套协作模型收窄到一个更具体的场景：**用户本机上的软件开发 Agent。**

## 对 Raft 的研究结论

参考资料：

- [Raft 欢迎页](https://docs.raft.build/welcome/)
- [Agent 基础](https://docs.raft.build/features/agents/)
- [Runtime](https://docs.raft.build/features/agents/runtime/)
- [外部 Agent](https://docs.raft.build/features/agents/external/)
- [计算机](https://docs.raft.build/features/server/computers/)
- [任务](https://docs.raft.build/features/collaboration/tasks/)
- [活动流](https://docs.raft.build/features/messaging/activity/)
- [文件评论](https://docs.raft.build/features/collaboration/comments/)

Raft 做对了这些事：

- Agent 是持续存在的成员，而不是一次性的聊天会话。它们有名字、描述、记忆、成员关系和工作历史。
- Runtime 可替换，并尽量保留用户已有的订阅和本地环境。这让协作层不被某个模型供应商锁死。
- 任务是可追踪的工作单元，有编号、状态和负责人；领取任务可以减少重复劳动。
- 线程承载细节，活动流负责让人快速补课。人不必读完所有消息，只需要看未读、提及和待审查事项。
- 执行计算机与协作服务分离。协调发生在共享空间，实际执行发生在某台机器上。
- 文件评论可以锚定到具体产物位置，使审查有明确上下文。

不应照搬的部分：

- 第一版不做“面向 Agent 的 Slack”。对开发者而言，任务、diff、终端、测试和仓库状态比频道更重要。
- 第一版不做身份联邦、插件市场、OAuth、移动端和团队权限。
- 不要过早抹平不同 Runtime 的差异。开发者需要知道 Claude Code、Codex CLI、OpenCode 的能力、失败方式和审批方式不同。
- 不要让 Agent 从第一天就自由互聊并自动决策。最先建立信任的方式是让人的观察和审查足够清晰。

## 产品判断

### 核心切入点

选择“本地 Agent 控制室”，而非“多 Agent 协作平台”。

前者说明了用户、场景、位置与首要动作：一个开发者在一个仓库内监督多个编码 Agent。后者范围太大，容易在还没有验证价值前变成聊天、任务管理和权限系统的拼盘。

### 令人想继续用的时刻

用户输入一个较大的目标后，控制室给出可编辑的任务拆分，随后让多个 Agent 在隔离工作区中执行。用户能同时看到：实现 Agent 的进度、测试 Agent 的输出、审查 Agent 的意见。系统在有 diff、测试结果、风险提示和推荐合并顺序时停下来，请用户做最终判断。

这不是“和机器人聊天”，而是“监督一个小型工程团队”。

### 产品前提

1. 长期有价值的是协调层，不是模型智能本身。
2. 第一类用户是熟悉编码 Agent 的个人开发者，而不是泛化知识工作者。
3. 最小闭环是一个仓库、一个人、一个任务、一个 Agent、一次审查；并行是下一阶段。
4. 首个信任基础是可见性：状态、日志、diff、检查点与审查决定。
5. 复用本地 CLI，因为它们已经具备文件系统和开发工具访问能力。
6. 所有 Agent 输出在人工验收前均视为未受信任。
7. 先验证本地编排，再讨论远程机器、多人协作和 Agent 间自治。

## 方案比较

### 方案 A：本地 Agent 控制室，推荐

本地 Web 应用或桌面应用，发现或配置本地 Agent CLI，创建隔离会话，分配任务，流式展示日志，跟踪状态，并提供审查界面。

优点：最短路径能做出真实演示；避开早期云端认证、计费和团队权限；直接服务开发者自己的痛点；可在软件开发工作流中与 Raft 形成差异。

代价：跨平台进程管理有复杂度；本地进程控制需要可靠；人与人协作暂缓。

可复用能力：已有 CLI、Git worktree、终端会话管理和 SQLite。

### 方案 B：人和 Agent 的在线协作工作区

做一个托管的服务器、成员、频道、任务和活动流系统，Agent 通过本地桥接程序加入。

优点：更接近 Raft 的完整协作模型，也为团队协作铺路。

代价：认证、实时同步、权限、部署、外部 Agent 连接协议同时出现，过早放大问题；很容易退化成普通任务软件加一点 Agent。

结论：作为长期方向保留，不进入前两个原型。

### 方案 C：Agent 审查面板

用户自行运行 Agent，应用只导入会话、日志和 diff，集中进行比较与审查。

优点：最小、风险低、直接命中“是否接受改动”的高信任时刻。

代价：没有任务分配和实时协调，魔法感不足，更像报告工具。

结论：若本地进程编排的技术验证失败，降级为此方案。

## 范围与阶段

功能树是实现范围的唯一索引，见 [功能树](../specs/feature-tree.md)。所有新增功能都必须先挂到树中的节点，并标注所属阶段。

### 原型 0：界面假数据验证

目的：不接入真实 Agent，验证控制室、会话页和审查页是否让人一眼理解。

- 三个假的 Agent 席位和任务卡片。
- 模拟日志、状态变化、待输入和待审查。
- 可点击的接受、驳回、发送反馈。

不验证：进程控制、worktree、真实 diff 采集。

### 原型 1：一个真实任务的端到端闭环

目的：证明一个人可以在浏览器中监督一个真实编码 Agent，看到日志和 diff，并作出可持久化的验收决定。

用户路径：

1. 打开一个本地仓库。
2. 配置一个命令行 Runtime，先支持通用 shell 命令。
3. 创建一个 Agent 席位，例如“实现者”。
4. 创建并领取一个任务。
5. 在隔离的 Git worktree 中启动会话。
6. 实时看到状态、终端输出、改动文件、阻塞信息和问题。
7. 会话结束后进入审查，查看摘要、diff、测试输出和未解决问题。
8. 人选择接受、驳回或带反馈退回。

必须有：

- 仓库选择与持久化配置。
- 一个 Agent 席位和一个通用 shell 适配器。
- 单任务看板与严格状态。
- 一个 worktree 或明确的隔离失败提示。
- 终端输出流。
- 改动文件、Git diff、退出码与测试输出。
- 接受、驳回、退回反馈，以及会话归档。

不做：Runtime 自动发现、多个席位、并行执行、暂停恢复、活动收件箱、合并队列、团队与云端。

### 原型 2：并行控制室

目的：恢复多 Agent 控制室的核心体验，但仍限定在一个人的本机和一个仓库内。

- 可配置或发现至少两个 Runtime。
- 2 到 3 个 Agent 席位，例如实现者、测试者、审查者。
- 多个隔离任务并行运行。
- 大目标拆分为可编辑的任务建议。
- 汇总“需要输入”“待审查”“失败”的活动收件箱。
- 跨会话的合并顺序和冲突提醒。

### 暂不纳入

- 团队账户与多人实时协作。
- 云端托管执行与远程机器。
- 移动端。
- Agent 间自主规划和自动互相派工。
- OAuth、市场和插件生态。
- 通用频道系统与完整文件评论。
- 计费和复杂权限。

## 原型 1 的实现契约

### 技术选型

- 形态：本地 Web 应用。
- 前端：React 或 Next.js，按项目启动成本最低者决定。
- 后端：Node.js 进程管理服务。
- 存储：SQLite。
- 进程执行：伪终端或子进程封装。
- 隔离：每个任务尽可能创建 Git worktree。
- 首个适配器：通用 shell 命令适配器。

这个组合不涉及桌面打包与云端认证，但已经覆盖关键难点：进程控制、流式事件、状态保存、worktree 隔离和审查。

### 任务状态

任务状态是看板上的用户状态，必须只使用这一组：

- 待开始（`todo`）：已创建，尚未领取。
- 已领取（`claimed`）：已分配给某个席位，尚未启动。
- 执行中（`running`）：进程正在运行。
- 等待输入（`needs_input`）：Agent 提问、等待审批或超时后需要人决定。
- 审查中（`in_review`）：已收集到可审查产物。
- 已接受（`accepted`）：人工通过。
- 已驳回（`rejected`）：人工不接受。
- 已失败（`failed`）：进程异常退出或无法收集必要产物。

Raft 的“待办、进行中、审查中、完成、关闭”是灵感来源；本产品额外区分“等待输入”和“失败”，因为它们是开发 Agent 场景中不同的人工动作。

### 会话状态

会话状态是进程管理内部状态，与任务状态分离：

- 启动中（`starting`）
- 运行中（`running`）
- 停止中（`stopping`）
- 已退出（`exited`）
- 失败（`failed`）
- 已超时（`timed_out`）

### 适配器契约

每种 Runtime 适配器必须实现以下能力：

- `validate`：验证配置的命令是否可执行。
- `start`：在指定工作目录中为一个任务启动会话。
- `sendInput`：将人工反馈或继续指令写入标准输入。
- `stop`：先请求优雅停止，超时后强制结束。
- `streamOutput`：按时间戳输出 stdout 与 stderr 片段。
- `collectArtifacts`：返回改动文件、Git diff、退出码和可选测试输出。

通用 shell 适配器的输入为：`command`、`args`、`cwd`、`env`、任务提示词与 `timeoutSeconds`。

原型 1 只要求可靠采集原始输出和进程生命周期，不假设任何外部 CLI 都有结构化状态。只有能被证明的状态才可自动推断。

### 事件

最小事件集：

- `session.started`
- `output.chunk`
- `task.needs_input`
- `artifact.changed_files`
- `artifact.diff_ready`
- `session.exited`
- `session.failed`

事件既用于界面实时更新，也写入本地数据库，便于会话回放和问题排查。

### 最小数据模型

| 对象 | 必需字段 | 用途 |
| --- | --- | --- |
| 项目 | `id`、名称、路径、创建与更新时间 | 一个本地仓库 |
| Agent 席位 | `id`、项目、名称、角色、适配器、命令、参数、环境变量 | 一个可复用的执行角色 |
| 任务 | `id`、项目、标题、描述、状态、负责人、worktree、分支 | 一个可审查工作单元 |
| 会话 | `id`、任务、席位、状态、进程 ID、起止时间、退出码、失败原因 | 一次实际执行 |
| 事件 | `id`、会话、类型、载荷、创建时间 | 可流式回放的事实记录 |
| 产物 | `id`、任务、类型、路径、内容哈希、元数据 | diff、日志、测试输出等 |
| 决定 | `id`、任务、决定、备注、创建时间 | 接受、驳回、退回等人工判断 |

### 失败处理

| 情况 | 会话状态 | 任务状态 | 用户看到的动作 |
| --- | --- | --- | --- |
| 命令不存在 | 不创建 | 待开始 | 配置错误与重新验证 |
| 创建 worktree 失败 | 不创建 | 待开始 | Git 错误与重试 |
| Agent 长时间无响应 | 已超时 | 等待输入 | 继续等待、停止或重试 |
| 非零退出码且无 diff | 失败 | 已失败 | 退出码与最后输出 |
| 非零退出码但有 diff | 失败 | 审查中 | 带警告审查结果 |
| 无法检测改动文件 | 失败 | 已失败 | 采集失败原因 |
| diff 为空 | 已退出 | 审查中 | “无改动”产物 |
| 用户要求停止 | 停止中，随后退出或失败 | 等待输入或已失败 | 终止结果与下一步选项 |
| 接受时出现合并冲突 | 已退出 | 审查中 | 冲突详情，不自动覆盖 |

### 界面验收标准

控制室：

- 用户能选择本地仓库。
- 用户能创建一个带 shell 命令的 Agent 席位。
- 用户能创建并启动一个任务。
- 状态变化无需刷新页面。

会话页：

- 进程输出出现后 1 秒内能显示在页面上。
- 停止按钮能结束会话。
- 失败会话显示退出码和最后一段输出。
- 若进程支持标准输入，用户可发送追问或反馈。

审查页：

- 能显示改动文件列表与 Git diff。
- 能显示退出码和已采集的测试输出。
- 接受、驳回、退回反馈会持久化。
- 接受后任务为“已接受”，驳回后任务为“已驳回”。

### 一周技术验证

在打磨界面前，先独立证明以下链路：

1. 为测试仓库创建一个 worktree。
2. 在该 worktree 内运行一条配置好的 shell 命令。
3. 将输出流式发送到本地网页。
4. 可以停止或超时终止进程。
5. 检测改动文件并采集 `git diff`。
6. 将会话事件写入 SQLite。
7. 在审查页显示产物，并保存接受或驳回决定。

若任何关键环节不可稳定实现，立即回退到“Agent 审查面板”，不要用更多抽象去掩盖问题。

## 产品对象

- 项目：一个本地仓库或工作区。
- Runtime：一个被配置或发现的 Agent CLI 提供者。
- Agent 席位：带有 Runtime、模型配置、审批模式和默认提示词的持久角色。
- 任务：有一个负责人、一个状态和一组审查产物的工作单元。
- 会话：某个席位为某个任务启动的一次执行。
- 产物：diff、文件、日志、截图、测试输出或总结。
- 检查点：Agent 需要人工输入或审批的时刻。
- 决定：接受、驳回、重跑、合并、丢弃或修改提示词。

原型 1 中，“审批模式”只表示人工对停止、接受、驳回和最终合并的本地控制，不引入通用权限系统。

## 体验原则

- 首屏是工作室，不是营销首页。
- 任务看板与活跃会话应同时可见。
- 用户始终能够看到谁在工作、在改什么、是否受阻、什么等待审查。
- 不以聊天为主；聊天或反馈服务于工作状态。
- 所有风险动作都有清晰审查界面。
- diff 是一等产物，不能藏在日志附件里。
- 被停止或失败的 Agent 应该显得可恢复，而不是神秘消失。

## 首批界面

### 项目控制室

左侧导航：项目、Agent、Runtime、活动、设置。主区域同时呈现任务看板、活跃会话和高亮的审查收件箱。

### Agent 会话页

显示 Agent 名称与 Runtime、任务标题、状态、终端输出、改动文件和当前计划。动作包括暂停、提醒、停止、请求总结。原型 1 只实现必要的停止和发送输入，其他动作留给原型 2。

### 审查页

显示 Agent 总结、diff、测试输出、风险提示与反馈框，并提供接受、驳回和退回控制。这是最关键的页面，必须让人能快速作出判断。

## 风险

- 外部 CLI 未必提供足够的结构化状态。缓解方式：先可靠采集终端输出、diff 和进程状态；再让特定适配器逐步增强。
- 并行 Agent 可能改到同一文件。缓解方式：每任务一个 worktree，并显示明确的合并和冲突队列。
- 用户不信任自主执行。缓解方式：默认停在可见检查点，所有改动先审查。
- Runtime 的体验改变可能破坏适配器。缓解方式：适配器保持薄，始终保留通用 shell 适配器。
- 产品可能变成普通项目管理工具。缓解方式：仓库状态、终端、测试和 diff 必须是一等界面元素。

## 成功标准

### 原型 1 成功的标志

- 用户能在 2 分钟内连接一个仓库。
- 用户能手动配置一个 Runtime 命令。
- 用户能启动一个隔离任务。
- 页面清晰展示该任务、该 Agent 与该工作区的归属关系。
- 页面实时展示执行过程。
- 任务进入审查时有 diff 与测试输出，或明确的“无改动”产物。
- 用户能在审查页接受或驳回。
- 完整演示可在 3 分钟内完成，并能用一句话说明价值。

### 原型 2 成功的标志

- 至少可使用两个 Runtime，自动发现失败时允许手动配置。
- 用户能并行启动三个隔离任务。
- 活动收件箱能跨会话汇总“待审查”“等待输入”和“失败”。

## 分发路径

个人项目阶段先作为本地 Web 应用或本地桌面应用，通过 GitHub Releases 分发，之后再考虑一条命令安装。

只有当单人控制室被证明有用后，才考虑签名桌面包、可选云端协调、团队账户和适配器 SDK。

## 下一步

1. 根据功能树制作三个核心界面的低保真假数据原型：控制室、会话页、审查页。
2. 用一个真实仓库跑完“一周技术验证”。
3. 只接入一个真实适配器，优先通用 shell 适配器。
4. 接入 Git worktree 和 diff 采集。
5. 完成可接受/可驳回的审查闭环。
6. 验证通过后，再进入原型 2 的并行、多 Runtime 与活动收件箱。

## 上线前的人工演练

在写代码前，先在同一个仓库手动开三个终端：一个 Agent 做小功能，一个写或修测试，一个审查 diff。记录每一个协调不顺的时刻：忘了谁在做什么、两个 Agent 改了同一文件、不知道是否被卡住、想暂停、希望有统一审查入口。

这些真实的摩擦就是第一版界面的来源。不要让理论抢在观察前面。
